00

结论速览

先给结论：业界反复出现的共性做法只有四条主线，落地上用「一个业务闭环」而非「一个大平台」起步。

一条主线：正式知识 = 内容 + Schema 映射 + 元数据 知识不是"先写完正文、再补元数据、最后才想 Schema"。正确做法是：围绕业务任务先定义最小元数据规范 + 最小业务 Schema，加工时同步产出内容、Schema 映射与逐条元数据，经业务确认后形成同一版本的正式知识。
一条铁律：使用结果不能自动改写正式知识 一次纠错可能只是个人偏好、例外或误反馈。真实链路是：使用记录 → 问题归因 → 业务负责人确认 → 提交待验证版本 → 评测决定上线或回退。原始来源、确认区、确认理由、复测结果和可回退版本都必须保留。
两条边界：别把概念混在一起 ①「知识生产」是基础流程，不是第五项治理——元数据贯穿全程，Schema 约束加工与解释，飞轮产生改进建议，评测决定版本是否生效。
② 元数据的 Schema ≠ 业务的 Schema：LinkedIn / Uber 文档里的 Schema 是「元数据模型」，而业务 Schema 由业务定义对象、指标与规则。
一个提醒：公开数字要区分口径 案例结果分属不同类型：工程效率自报测试（Meta）、上线前离线质量（Microsoft）、部署后变化（阿里 OpenBG）、采用规模（LinkedIn）、整体项目结果（Jacobs × Palantir）、仅机制公开（Snowflake）。不横向排名，不把个案数字当行业承诺。
01

知识运行框架：四项治理如何连成完整链路

上面一条是知识生命周期，下面四个是治理能力。生命周期回答"知识怎么流转"，治理回答"每一段由谁管、管什么"——两者不是同一条顺序。

知识生命周期（主链路）

业务场景与原始来源TASK · SOURCE
最小元数据 / Schema 约束加工CONTENT · SCHEMA · METADATA
业务确认 → 正式知识CONFIRMED · VERSIONED
任务调用并留痕RETRIEVE · USE · ACT
形成待验证改进OBSERVE · REVIEW · SUBMIT
评测后更新或回退TEST · RELEASE · ROLLBACK

四项治理能力

治理核心要回答的问题关键动作常见产物
01 元数据每条知识是谁的、从哪来、谁负责、何时有效、现在能否用？贯穿全生命周期：定义字段 → 同步采集 → 持续维护知识档案 · 来源与派生链路 · 版本 / 状态
02 业务 Schema跨系统、跨团队怎样使用同一套业务定义？约束加工与解释：对象 / 关系 → 指标 / 规则 → 数据映射对象模型 · 指标定义 · 规则 / 例外
03 知识飞轮知识怎样被找到、调用，并从真实使用中发现问题？产生改进建议：查找材料 → 回答 / 动作 → 待验证改进模型材料包 · 调用记录 · 人工修改 / 结果
04 评测哪些改进可以进入正式版本？控制版本生效：固定测试集 → 版本对照 → 更新 / 回退期望结果 · 隔离测试集 · 影子对照
本次理解真正的飞轮不是"越用越自动写库"，而是越用越能发现缺口、归因问题、形成经负责人确认的改进建议；评测是版本生效的闸门，决定更新、拒绝或回退。
02

知识生产怎么做：先有最小约束，再加工、确认和版本化

五种做法可以串成一条通用加工链；六类公开方法又分成「通用原则 / 开放载体 / 企业实现」三组，六张卡不是连续步骤，而是可选的加工范式。

通用加工链（五步）

业务场景与来源明确任务，保留原文、数据和事件版本
加载最小约束必填元数据字段 + 最小业务 Schema
加工并同步生成整理内容，同时生成 Schema 映射与元数据
业务确认确认主来源、业务含义、范围、例外与状态
形成正式知识内容 + Schema 映射 + 元数据，统一版本

通用原则与开放载体

通用原则 · SOURCE FIRST

加工结果不能覆盖原始资料

原始资料不一定天然正确，但必须保留版本和来源；摘要、标签、关系和规则都应能追溯到原文。

source snapshot + source_id + captured_at
→ derived content + reference + version
→ review / replace / rollback

解决：发现加工错误时可重新核对、修正与回退。

通用方法 · KARPATHY LLM WIKI

定期整理，而不是每次问答临时重做

保留 Raw Sources，由模型持续维护摘要、实体页、概念页、交叉引用与变更日志，用文件组织规则约束加工流程。

raw sources → LLM read / merge / revise
→ wiki/{summary, entity, concept, index, log}
processing contract = AGENTS.md / CLAUDE.md

适合：长期研究与团队知识积累；属个人公开生产方法，不是企业治理标准。

开放载体 · GOOGLE OKF

用开放文件格式包装可交换知识

一个概念一个 Markdown 文件，YAML Frontmatter 保存可查询字段，普通链接形成关联，index / log 支持渐进读取与变更追踪。

bundle/{index.md, log.md, concepts/*.md}
--- type · title · description · resource
tags · timestamp --- + Markdown body + links

边界：OKF 是知识包格式，可承载部分元数据，但不能替代企业元数据治理、业务 Schema 或检索运行时。

三种企业实现

企业实践 · META CONTEXT FILES

按任务加工：把分散经验整理成 Agent 可读说明

Meta 让多个 Agent 扫描代码、文档与隐性经验，生成固定结构的 Context Files，再由 Persona 查询与周期刷新检查可用性。

code + docs + tribal knowledge
→ structured context file
→ persona query / critic review / refresh

特点：不复制全部原文，而是围绕任务压缩出导航、约束与操作说明。

企业实践 · ALIBABA OPENBG

结构化加工：实体、属性和关系对齐成知识图谱

先定义类目与关系，再从多源商品信息抽取实体、属性与关系，经对齐、消歧、质量检查后进入图谱和下游任务。

TBox / vocabulary → multi-source extraction
→ alignment / dedup / validation
→ ABox / graph → downstream tasks

适合：对象和关系稳定、需跨来源对齐和多任务复用的场景。

企业实践 · SNOWFLAKE VERIFIED QUERY

专家确认：把正确范例做成正式知识条目

Verified Query 保存自然语言问题、业务确认过的正确 SQL、验证人与时间；真实使用只能生成建议，确认后才纳入正式语义模型。

question + expected SQL + verified_by / at
usage history → suggestion
→ accept / edit / dismiss → version

特点：把"正确示例"从聊天记录变成有负责人、有版本的可复用内容。

一句话记住正式知识不是一段正文，而是「内容 + Schema 映射 + 元数据」三件套；最小 Schema 与元数据规范在加工前给出约束，逐条记录在加工时同步生成，而不是事后补登记。
03

治理 01 · 元数据：让每条知识说明来源、负责人和有效范围

元数据与内容同步产生，但职责不同：内容回答"知识说了什么"，元数据回答"这份内容是谁、从哪来、谁负责、现在能否用"。

主流思路 · KNOWLEDGE AS PRODUCT元数据不是知识正文，而是知识的管理说明：知识 id / 类型、来源与原文、负责人（maintainer）、权限范围、有效时间、版本与状态、质量状态、派生来源链路。
knowledge_id / typesource / 原文maintainerACL / scopevalid_timeversion / statusquality_status / last_checkedderived_from / lineage

为什么元数据不能只登记一次？

  • 知识变化比人工维护快，关键运行状态应尽可能从系统和使用记录中自动采集。
  • "有人写过"不等于"现在可用"——必须能找到负责人并判断是否仍然适用。
  • 模型需要权限和来源信息，才能决定能否取用、怎样引用，以及资料不足时是否停止回答。

建议建设链：MODEL → CAPTURE → CONFIRM → OBSERVE

  1. 定义元数据模型 —— 确定知识类型、必填字段、状态枚举和来源关系。
  2. 加工时自动采集 —— 采集来源版本、时间、权限、派生链路与质量检查结果。
  3. 确认责任与状态 —— 确认主来源、负责人、适用范围、复核周期和生效状态。
  4. 事件驱动维护 —— 来源变更、到期或质量异常时更新状态并触发复核。
交付物：元数据字段规范 · 知识档案卡 · 状态与质量规则

案例速览：同一件事的两种公开做法

LINKEDIN · DATAHUB（2019 官方工程博客）

用 Entity / Aspect / Relationship 统一元数据模型

把数据集、指标、AI Feature 等资产与负责人、组织、状态和关系接入同一元数据图。

当时公开规模：100 万+ 数据集 · 2.5 万指标 · 1,500+ 周活员工。这是资产管理模型，不是业务对象定义。

UBER · DATABOOK（官方工程博客）

领域团队维护元数据类型，中央团队审核兼容性

Dragon 统一 Entity / Value Type 定义，工具生成兼容模型；负责人、描述、使用、质量、时效、资产关系和隐私信息进入统一页面。

注意：这里的 Schema 是"元数据模型"，不是下一页的业务 Schema。

业务要参与确认主来源、负责人、适用范围、权限分类与复核周期技术负责字段规范、自动采集、版本、状态与异常提醒
04

治理 02 · 业务 Schema：让跨系统、跨团队使用同一套业务定义

业务 Schema 不是知识档案，而是一套共同业务定义：对象、属性、关系、指标、规则、约束和例外；需要操作时再定义 Action 契约。

对象 / 属性关系指标 / 规则约束 / 例外Action 契约（需要操作时）

本体、知识图谱、语义层分别解决什么？

本体定义对象类型、属性、关系和约束；涉及操作时可增加 Action 参数、前置条件和影响对象。
知识图谱承载实体与关系，支持跨来源关联和多步查询，但不会自动获得执行权限。
语义层统一指标、维度和问数口径；小场景可先用术语表、指标表和规则表。

建议建设链：SCENARIO → MINIMUM MODEL → MAPPING → VALIDATE

  1. 锁定业务任务 —— 明确要回答、判断或操作什么，以及错误代价。
  2. 定义最小 Schema —— 从代表样本梳理对象、关系、指标、规则和例外。
  3. 映射真实来源 —— 把业务定义映射到表、列、文档、API 和工具。
  4. 任务验证并迭代 —— 用真实问题验证覆盖与歧义，版本化后逐步扩展。
交付物：领域词表 / 对象模型 · 指标 / 规则 / 例外 · 数据与 Action 契约映射

案例速览：同一件事的两种公开做法

PALANTIR · ONTOLOGY（官方文档）

业务模型与运行时治理组合：从对象理解走到受控动作

Ontology 定义对象、属性、关系与逻辑；Foundry 再把 Action、安全规则和运行记录组合进运营平台，供人员、应用和 Agent 共用。

边界：Schema 定义动作契约；权限、审批、执行与审计属于运行时。

SNOWFLAKE · SEMANTIC VIEW（官方文档）

指标问数更适合语义层：维度、Fact、Metric、关系与同义词

Semantic View 用逻辑表、维度、事实、指标和关系覆盖并映射物理表；Verified Query 保存问题及业务确认过的正确 SQL。

治理重点：统一分析口径与自然语言问数。

业务要参与提供真实任务、代表样本、词义、指标口径、规则与例外技术负责建模工具、来源映射、一致性校验、版本和兼容

治理 03 · 知识飞轮：调用、留痕与改进

知识飞轮分上下两段：上半段回答"知识在一次任务里怎么被用"（先过滤 → 再查找 → 再组装）；下半段回答"使用结果怎样变成可信的改进建议"。它只产生建议，不决定上线。

六种查找方式怎么选（查询路由）

方式适用场景做法权衡 / 注意
A · 全量材料材料很少，可以整体交给模型whole corpus → permission filter → cache → model是否整体放入取决于长度 / 成本 / 更新频率 / 权限，不存在统一数量门槛。
B · 文件原生查找文件不多、结构清楚、性能要求不高index → Glob → Grep → Read neighbors → cite透明、无需额外建向量索引；可复用文件权限，但仍须在检索与生成时强制执行。
C · 混合检索
Contextual RAG		文本较多，既有精确术语也有同义表达metadata / ACL → keyword + dense → fusion → rerank覆盖面与成本的常见均衡起点；切块、上下文化和返回数量要用固定测试集调优。
D · 图检索
GraphRAG		跨文档、多步关联或整体归纳question type → local | global | drift | basic建图和实体对齐有成本，只用于普通检索难以回答的问题；简单问题退回轻量检索。
E · 时态关系检索内容持续变化，须回答"某一时点是什么"ACL + valid time → keyword + semantic + graph适用组织关系、政策版本、客户状态、策略版本；需持续维护来源、失效和冲突。
F · 结构化直接查询指标和交易状态优先查询已确认口径的系统schema / metric / verified query → execute → explain不应先把表转成文本再做向量检索；执行操作按风险配置权限、条件和必要的人审。
本页只回答"怎么用"元数据决定能不能取用　·　业务 Schema 决定查什么、怎样解释　·　召回与检索决定找到哪些材料　·　组装决定最终交给模型什么。
知识飞轮 · 下半段

回流闭环：使用记录 → 归因 → 负责人确认 → 待验证版本

记录真实使用问题、取用材料、回答 / 操作、人工修改和结果
归因问题内容 / 时效 / Schema / 检索 / 规则 / 模型
业务负责人确认接受、编辑或驳回，说明适用范围和原因
提交待验证版本内容 / Schema / 检索或规则变更 + 补充测试样本

改进建议按性质分流处理：

个案 → 保留为特殊处理 共性 → 形成版本变更 错误 → 补充固定测试集
为什么不能"用户一改，知识就自动更新"？
  • 一次纠错可能只是个人偏好、特殊例外或错误反馈。
  • 未经确认的修改会把错误带入后续检索、规则和模型。
  • 必须保留原始来源、待确认区、确认理由、复测结果和可回退版本。
案例 · MICROSOFT CLOSED LOOP（官方产品博客）

先记住具体纠错，再从多条经验归纳通用规则

新规则版本与当前版本在影子环境中同时运行；统计结果达标后，才替换当前版本。

上线前离线测试：F1 +8.2pp；需人工修改字段 64% → 48%。

案例 · META BUSINESS OWNER REVIEW（官方工程博客）

把请求、调用过程、所用材料、输出和最终决定一起留下

业务负责人复核请求背景、所用材料和最终决定；真实历史请求进入评测，生产使用信号驱动每日复测。

共同点：真实运行记录 · 人工确认 · 可追溯 · 持续复测。

业务要参与判断改进项是通用规则还是一次例外，接受 / 修改 / 驳回并说明适用范围与原因技术负责完整留痕、问题归因、版本候选和测试样本生成
06

治理 04 · 评测：不是只看准确率，而是验收与持续复测机制

评测接住飞轮提交的待验证版本：业务负责人判断方向是否合理，但版本能否上线，要靠可重复的测试。

真实评测六步流程

接收待验证版本变更范围、风险与错误代价
建设测试集真实请求、边界、失败与权限样本
隔离数据保留测试集、时间切分与防泄漏
分层打分知识、检索、回答 / 操作、业务四层
版本对照当前版本 vs 待验证版本，多次运行
决定上线影子对照、小范围试运行、监控与回滚

每条测试样本都能还原一次真实业务任务

不只保存"问题—答案"，还应保存：
① 谁在什么时间、带什么权限发起什么任务
② 应依据哪些资料或数据，给出什么回答或操作
③ 哪些内容或操作禁止；资料不足时是否停止回答或转人工
④ 谁标注、为什么这样判、错误会造成什么影响

样本切片覆盖四类：

正常主干：高频任务与核心口径 边界 / 反例：缺信息、歧义、越权、冲突 历史失败：每次事故固化为回归样本 时间 / 权限：旧版本、角色、租户隔离

四层评测指标

层级看什么示例指标
知识本身质量 + 硬约束完整率、重复 / 冲突率、时效性、负责人是否明确；权限 / 来源 / 版本 / 有效期与失效状态是否正确
检索 / 材料找到多少 + 带入多少噪声Recall@K、Claim Recall、Context Coverage；Context Precision、权限 / 时间正确、引用覆盖
回答 / 操作任务质量 + 风险Exact / F1 / SQL 结果、任务成功、回答是否有来源支撑；编造、错误拒答、错误操作、敏感信息暴露
运营 / 业务效率 + 场景结果p50 / p95 延迟、Token / 成本、人工修改率；采用率、解决率、耗时、CTR / GMV 等业务指标

企业官方公开的评测做法

PALANTIR · AIP EVALS

Suite = 测试样本 + 待测函数 + 评价函数；可设布尔 / 数值目标。LLM 任务建议至少运行 3 次，每轮指标都满足目标才算通过。

MICROSOFT · POWER APPS

100 张发票 × 10 次独立运行 × 4 配置，报告均值与 95% CI；待验证版本先影子对照，再用假设检验 + 功效分析决定是否替换。

SNOWFLAKE · EVALUATIONS

选中的 Verified Query 从临时语义视图移除以防泄漏；比较生成 SQL 的执行结果，记录 Accuracy、Regression 与 Latency。

本次建议的上线条件公开标准尚未给出跨任务、跨行业通用的 Recall 或 Groundedness 数值阈值。企业应在固定测试集中明确：不得出现越权访问或高风险错误操作；再按任务类别设质量、成本和延迟阈值。知识、Schema、检索或 Prompt 变更都应跑同一套回归。

深拆案例：五家代表实践，按同一副框架核对

每家按「知识生产 + 元数据 / 业务 Schema / 使用与闭环 / 评测」四个维度拆解。公开到什么程度就写什么，未披露的缺口标黄、不做推断。每案底部附「公开口径」边界。

COMPANY CASE 01 · PALANTIR ONTOLOGY

Palantir：把企业知识建成"可执行的运营模型"

知识形态：业务对象 + 当前状态 + 逻辑 + 动作 + 权限。用于水厂、工厂、医院等跨系统运营决策；重点不是再造一张数据表，而是形成业务人员和系统共用的实时运营语义层。

01 · 知识生产 + 元数据

Object Type 的公开结构

Object Type · backing dataset · primary key
Property {name, type, required, status}
Link Type · Interface · Role
  • 映射：Dataset / Row / Column / Join → Object Type / Object / Property / Link。
  • 治理：校验主键唯一与必填；属性标记 experimental / active / deprecated，Branch 评审后发布。
客户的实体消歧、来源优先级与质量阈值未统一披露
02 · 业务 Schema

Schema 同时装"名词、关系、逻辑、动作"

Aircraft ─assignedTo→ Flight
Property: status / capacity · Function: available?
Action: reassignAircraft() · Security 贯穿各层
  • 建模：业务名词→Object；关系→Link；计算 / 模型→Function；业务动词→Action。
  • 复用：Shared Property 统一字段；Interface 统一跨对象能力；端到端 Branch 测试后合并。
它不是"表换名"，而是可执行的决策 / 运营本体
03 · 供给 / 使用 / 闭环

一次业务动作会留下可治理的决策记录

Action {parameters, rules, submission criteria,
permissions, notification / webhook, undo}
Log {type+version, time, actor, objects, parameters}
  • 执行：应用 / Agent 读授权对象 → 调用 Action → 校验条件与权限 → 事务性修改对象 / 关系。
  • 回流：新状态进入 writeback dataset，Action Log 与对象关联，供监控、复盘与下一轮决策。
日志会沉淀；是否自动升级规则或训练模型由客户实现
04 · 评测

评测工件是 Suite，而不是一张"准确率表"

TestCase {input, expected output}
+ Target Function + Evaluator
→ metric / pass-fail / cross-run variance
  • 测试集：人工边界案例或真实 Object Set；可用 exact、regex、数值、LLM judge 或自定义函数。
  • 上线评审：比较模型 / Prompt / 历史版本；Ontology 编辑先在模拟环境执行，再结合 Branch / Release 评审。
能力公开；客户题集规模、业务阈值与自动阻断策略未披露
≈ −20%Jacobs 某水厂全厂用电（原案例口径）
+33%Airbus A350 交付速度（原案例口径）
公开口径Jacobs 与 Airbus 数字来自官方合作材料，反映不同整体项目的自报结果；不是独立第三方评估，也不能单独归因于 Ontology 或 Actions。客户私有 Schema、测试集与阈值未公开。
COMPANY CASE 02 · ALIBABA OPENBG

阿里 OpenBG：按知识类型组合建模十亿级电商知识

知识形态：RDF/OWL 本体 + SKOS 概念 + 属性图 + 规则。商品类目、消费概念、实体关系和商业规则不硬装进一种模型，而是按知识类型分别建模，再统一形成可训练、可查询的 TBox / ABox 资产。

01 · 知识生产 + 元数据

公开工件：TBox + ABox + Benchmark

TBox: Class / Concept / Relation + domain / range
ABox: Product ─brandIs / relatedScene→ Entity
字段：label · subClassOf / broader · type · comment · image
  • 原料：淘宝标题、详情、图片、评论、搜索词 + Wikidata / OpenKG / 品牌官网。
  • 加工：NER / 关系抽取 / 指代消解 / 人工标注 → 标准名与同义词对齐 → Jena 生成 TBox / ABox。
支持 TTL / NT / JSON-LD / OWL；负责人、版本、有效期、权限字段未披露
02 · 业务 Schema

不同知识类型采用不同 Schema

Category / 属性 → RDF / OWL Ontology
Scene / Crowd / Theme / Time / Market → SKOS
商品 / 品牌 / 地点关系 → Property Graph
商业规则 → Rule Model
  • 类目：专家自上而下建树，以清晰、完整、互斥、热度、认可度每日审核。
  • 概念：从评论 / 搜索词用 BERT-CRF 抽取、自下而上归纳；品牌和地点做 Schema Mapping。
Rule Model 仅披露 20 万+ 规则待发布，语法与样例未公开
03 · 供给 / 使用 / 闭环

知识被编译进模型和具体交易任务

KG triples + 商品文本 / 图片
→ KG-enhanced mPLUG 预训练 → 任务微调
→ 商品对齐 / 导购 / AliMe QA / 新品属性填充
  • 使用：同一套知识分别进入类目预测、NER、摘要、评论 IE、显著性判断与线上业务。
  • 维护：每日新增数据 → 专家质检 → 修订类目 / 概念 / 三元组 → 持续调整 ontology。
公开的是生产维护小循环；点击 / 纠错如何审批回写未披露
04 · 评测

从 Schema 质检一直测到线上 KPI

Schema QC → KG Benchmark → 下游任务 → 线上业务
Hits@K / MRR · Accuracy / P-R-F1 / ROUGE-L
GMV · CPM · CTR · 上新时长
  • 题集：训练 / 验证 / 测试三元组；下游验证集排除在预训练数据外，避免标签泄漏。
  • 业务：部署后报告商品对齐 GMV、导购 CPM、推荐 CTR 与上新时长变化。
生产准入阈值、线上分流、样本量与显著性未披露
2.6B / 88M+三元组 / 实体（论文公开规模）
≈ +11% / ≈ −30%推荐 CTR / 新品发布时长（部署后自报）
公开口径论文强在构建、Schema、应用和部署后结果；未披露负责人、权限、生命周期、上线审批，以及业务指标的实验分流与显著性细节。
COMPANY CASE 03 · META

Meta：两套独立实践，分别拆工程上下文与访问决策知识

不是统一系统。前者把隐性工程经验做成 Context File；后者把资源层级、数据图、SOP 与请求上下文用于访问决策。页面并列看的是两者共同的工程模式。

01 · 知识生产 + 元数据

一套做工程导航，一套做决策上下文

A · Context File {Quick Commands, Key Files,
Non-obvious Patterns, See Also}
B · Resource {Table, Column, Dashboard,
Policy, SOP} + summary / semantics
  • A 加工：2 个探索 Agent → 11 个模块分析 → 2 个写作 → 10+ critic 三轮 → fixer → Router 优化。
  • B 加工：资源层级、Wiki / 规则、用户 Profile / 近期活动、Query shape 被组合成可读上下文。
A 未公开 Owner / 版本字段；B 未公开 Resource 完整字段表
02 · 业务 Schema

两个任务各有自己的轻量 Schema

A · Module → files / commands / hidden
constraints / depends-on / related modules
B · Resource Graph + Role + SOP +
Explicit / Implicit Intent + Context
  • A 约束：每个模块固定 25–35 行、约 1,000 tokens，并补跨仓依赖索引与 Data Flow Map。
  • B 约束：资产节点、生产 / 消费 / 访问边、资源层级与数据语义，再叠加角色和业务意图。
都不是企业级 Ontology；正式版本与审批 Schema 未披露
03 · 供给 / 使用 / 闭环

留下的记录与回流方式也不相同

A · Task → Router → Context File；路径 /
覆盖 / critic 结果驱动周期刷新
B · Query + trace + used context + output
+ decision / log → Data Owner review
  • A 闭环：每隔数周验证路径、覆盖缺口和过期引用，重新运行 critic 后修复。
  • B 闭环：User Agent 推断意图，Owner Agent 定位资源；规则护栏后保存决策，Owner 反馈进入评测。
B 未说明反馈会自动改 SOP；A 是鲜度闭环，不是业务纠错闭环
04 · 评测

一个用 Persona 题集，一个用真实请求日回归

A · 55+ questions × 5 personas → critic
score / path validity / tool & token use
B · historical request + activity + profile
+ query run + final decision → acc / recall
  • A 结果：三轮 critic：3.65 → 4.20 / 5；引用路径全验证；公开报告零路径幻觉。
  • B 上线条件：从真实历史请求建集并每日回归；运行时另有查询权限、每日预算和规则型风险护栏。
评分 rubric、题集规模 / 切分及统一发布阈值未公开
4,100+工程上下文实践：覆盖文件
≈ 2 天 → 30 分钟理解复杂数据管道（案例自报）
≈ −40%6 项初测任务：工具调用与 Token
公开口径本页并列归纳两套独立实践："运行记录 + 数据负责人反馈 + 每日回归"只对应数据仓访问实践，不代表两套系统已经打通；6 个初测任务的结果不能代表全公司统一 ROI。
COMPANY CASE 04 · MICROSOFT POWER APPS

Microsoft：把每次业务纠错沉淀为可复用规则

知识形态：结构化纠错记忆 + 租户 / 流程内的业务规则。以发票数据录入为例：用户不只修正这一次结果，系统把纠错变成记忆，再把高频经验蒸馏为可验证、可升级的组织级规则。

01 · 知识生产 + 元数据

原始文档、草稿与纠错怎样变成记忆

Input: PDF / Excel / Email
Target: Dataverse Table + Logical Columns
Draft: Suggested Values
Feedback: old → corrected
Asset: Structured Memory
  • 生成：invoke_data_entry 接收原文、目标表和待预测列，抽取 Supplier / Address / Country / Total 等字段并生成草稿。
  • 加工：Agent Feed 左看原文、右看建议；业务用户修改并保存，每次差异持久化为可检索记忆。
记忆真实字段、相似度键、Owner、保留期、访问控制与版本未披露
02 · 业务 Schema

知识分成"案例记忆 + 通用规则"两层

Example Memory {business context, correction,
reusable handling}
Generalized Rule {condition → instruction}
例：UK→United Kingdom · legal entity name · total incl. VAT
  • 数据层：Dataverse 用目标表 + Logical Column 约束结果结构；具体纠错先保留为流程范围内的示例。
  • 知识层：多条记忆经 Genetic-Pareto 蒸馏为规则，编译进 Candidate Prompt / Agent Instructions。
这是流程级 Rule Schema；规则存储格式与 Prompt 版本对象未披露
03 · 供给 / 使用 / 闭环

人工纠正先复用，再被蒸馏为组织规则

Draft Record → User Diff → Structured Memory
→ Similar-memory Retrieval → Generalized Rule
→ Candidate Prompt → Shadow Test → Baseline
  • 运行：Dataverse 记录在人工确认前不创建；下一次相似任务检索记忆并复用之前的处理方式。
  • 升级：周期性规则蒸馏，Candidate 与 Current Prompt 对同一输入并行评分，达标后自动晋升。
审核人就是处理数据录入的业务用户，纠错直接来自真实工作
04 · 评测

发布工件包含数据集、对照和统计门槛

100 invoices × 10 independent runs × 4 configs
4,277 field instances · mean + 95% CI
F1 66.4→74.6% · fields needing edit 64→48%
  • 质量：除 F1 外，还看业务用户能否"零修改直接保存"；共减少 1,045 个需人工修改字段。
  • 上线条件：Current / Candidate 影子并跑 → hypothesis testing + power analysis → 达统计阈值后升级 Baseline。
显著性水平、目标功效和每次升级最小样本量未披露
F1 +8.2pp66.4% → 74.6%
64% → 48%需人工修改字段（上线前离线模拟）
结果适用范围结果来自 UK Electoral Commission 数据集上的上线前离线模拟；产品机制已公开，不能外推成所有业务场景的生产收益。
COMPANY CASE 05 · SNOWFLAKE CORTEX ANALYST

Snowflake：把业务语义、验证问答与评测做成同一套资产

知识形态：业务语义模型 + 已验证问题 / SQL。面向自然语言数据分析，把指标、维度、关系、同义词和经过业务确认的问法统一管理；使用建议、人工审核和回归评测围绕同一对象运转。

01 · 知识生产 + 元数据

Verified Query 本身就是可治理知识工件

- name: California profit
  question: What was the profit …?
  sql: SELECT sum(profit) …
  verified_by / verified_at /
  use_as_onboarding_question
  • 生产：业务专家确认"自然语言问题—正确 SQL"，记录验证人 / 时间，加入 Semantic View / Model。
  • 治理：语义资产接 Snowflake RBAC、Tag；官方建议 YAML / DDL 进 Git 做评审、回滚与 CI/CD。
经确认的样例不是聊天记录，而是带验证信息的正式知识条目
02 · 业务 Schema

Semantic View 的字段与映射

Logical Table sales_data → database.schema.table
Dimension state {expr, type, description, synonyms}
Measure profit {expr: amt-cst, default_agg: sum}
Relationship orders.customer_id → customers.id
  • 设计：先定业务实体、关系、维度、Fact、Metric；建议从聚焦场景的 3–5 张表起步。
  • 映射：再映射物理表 / 列，补名称、描述、同义词、聚合与 Join Path，审核后 CREATE SEMANTIC VIEW。
规则型知识在 Semantic View；复杂范例型知识在 VQR
03 · 供给 / 使用 / 闭环

真实使用先产生建议，不能自动改写正式知识

Suggestion {type: VQ | filter | metric |
description | synonym,
evidence: query history / Analyst questions /
existing VQ,
decision: Accept | Edit | Dismiss}
  • 发现：从近期 SQL 和 Analyst 使用中找"高频且新颖"的缺口；每类最多展示 10 条建议。
  • 确认：领域人员 Accept / Edit 后进入 VQR 或语义层；正确范例还可抽象成可复用 Filter / Metric。
闭环核心：使用信号 → 改进建议 → 人工确认 → 新版语义知识
04 · 评测

同一 VQ 既可服务运行，也可成为防泄漏题集

Ground truth {question, expected SQL}
metric = sql_correctness
report = accuracy + regressions + latency
+ generated SQL
  • Holdout：选择 VQ 作为评测集；系统从临时 Semantic View 移除被测 VQ，避免 Exact-Match 泄漏。
  • 回归：生成并执行 SQL，与 Expected SQL 结果比较；审核 Improve 建议后重跑，确认提升且无回归。
截至 2026-07，内置评分 metric 仅 sql_correctness；未给统一自动发布阈值
机制链路公开资产、建议、人审与评测均有官方产品文档
未披露公司内部或客户的可归因业务收益
公开口径文档覆盖 Semantic View、VQR、人工确认建议与 SQL correctness 回归；不等于覆盖多轮对话、权限安全或所有质量维度，也未提供可归因业务收益。

阿里 OpenBG 电商推荐 / 业务指标（部署后） CTR +11%；商品发布时长约 −30% 统一 TBox / ABox → 多模态对齐 → 预训练 → 下游任务 企业参与论文自报；线上分流、样本量、显著性、长期归因未完整公开
LinkedIn · DataHub 平台采用规模 1,500+ 周活员工；覆盖 100 万+ 数据集 / 2.5 万指标 统一知识身份 → 搜索发现 → 责任与变更协作 2019 年公开的覆盖规模与采用度；不等于可归因财务收益
Jacobs × Palantir 运营决策（整体项目结果） 约 20% 全厂节电（Agua Nueva 项目）；另有 Airbus A350 交付 +33% 统一对象与状态 → 模型建议 → 结合现场流程执行 官方合作项目材料；整体项目结果，不能单独归因于 Ontology，不能外推其他工厂
Snowflake 产品机制（价值链路本身） 机制已公开；可归因客户结果未披露 调研原则：产品能力、测试结果、客户业务结果分开陈述 "没有公开数字"也是结论——避免为完整而编造统一 ROI
阅读方式这些案例展示的是不同类型的价值信号；场景、基线、测试层级和公开材料性质不同——不做横向排名，也不把个案数字当成行业承诺。

落地建议：先跑通一个业务闭环，再固化成知识运行规范

与开头同一张图：上方是知识生命周期，下方只有四项治理能力。先围绕真实任务起步，复杂度由真实需求触发，不预建大平台。

四项知识治理规范（统一运行标准）

01 · 知识档案 / 元数据

最小元数据模型，加工时同步记录

id / type / source / maintainer / ACL / scope / valid_time / version / status / lineage

02 · 业务 Schema

共同业务定义，操作再补契约

对象、属性、关系、指标、规则、约束与例外；涉及操作时补充 Action 参数、前置条件和影响对象。

03 · 调用与知识飞轮

留痕 → 归因 → 确认 → 待验证版本

权限与时间过滤 → 按任务检索和组装 → 回答 / 操作留痕 → 归因问题 → 负责人确认 → 提交待验证版本。

04 · 评测与版本更新

固定测试集 + 分层指标 + 版本对照

按风险采用影子或小范围试运行，决定更新、拒绝或回退。

分阶段建设建议

PHASE 1 · PILOT先做一个跨序列高价值场景

选代表来源，定义最小元数据与最小 Schema，加工出正式知识并建立固定测试集；小库优先文件或结构化查询。

PHASE 2 · OPERATE跑通调用、反馈与评测

建设使用留痕、负责人确认、待验证版本、回归测试、上线观测与回滚，形成可持续闭环。

PHASE 3 · UPGRADE按问题升级，不预建大平台

多跳全局问题再上 GraphRAG；高变化知识再上时态图；需要写回再上受控 Action。

建议最小合同（把公开锚点落到可执行字段）

对象最小合同字段依据
元数据 / 知识档案id · type · source · owner · version · status · effective_time · ACL · lineage · qualityDCAT 3 / PROV-O / ISO 25012 · LinkedIn / Uber
业务 Schemaconcept · object · property · relation · metric · rule · action · constraint · mappingRDF / OWL / SKOS / SHACL · OpenBG / Snowflake / Palantir
运行记录（飞轮）query · context_ids · output / action · trace · feedback · reviewer · decision · next_versionW3C DUV / PROV-O · Snowflake / Microsoft / Meta

重要边界"建议最小合同"是把标准与企业实践映射到本次场景后的落地模板，不宣称它本身是国际标准；尤其 RAG / Agent 评测目前没有跨行业统一的数值阈值。
业务负责选择场景、确认主来源与业务定义、维护例外、标注测试样本、决定风险阈值 技术负责加工与元数据采集、Schema 映射、检索运行时、版本留痕、自动复测与回滚
