Technical Selection Research / Graph Database

图数据库技术选型研究报告 企业做知识图谱 / 本体工程知识库时，到底该怎么选

本报告不回答「哪个图数据库最好」，只回答一个问题：给定你的本体形态、查询负载和数据规模，应该选哪一类、哪一款、以及什么时候不该选。 全篇按「先定模型 → 再定能力 → 再看产品 → 最后看触发点」的顺序展开，覆盖 20+ 主流产品与 2024–2026 年的标准、许可与市场变化， 并给出可直接执行的 PoC 验收清单与三阶段落地路径。
版本 v1.0 2026-09-11 面向：同程旅行 · 公共业务研发中心 调研范围：20+ 产品 / 2024–2026 公开资料 口径：厂商自报数字均标注来源性质

// 结论先行 · 7 条核心判断

  1. 先选模型，再选产品。「本体要不要形式化推理」这一刀，把候选池从 20+ 砍到 3–5 个。RDF/OWL 与属性图（LPG）不是同一道题的两个选项，混用会付出一次采购周期的代价。
  2. 多数企业知识库应该选 LPG。只有需要 OWL 形式化推理、合规可证明、或已持有行业标准本体（金融 FIBO、医药 SNOMED 等）时，才值得付 RDF 的代价。GraphRAG 时代的主流路径是「属性图 + 向量 + 全文」三路混合。
  3. 2026 年的分水岭是「混合检索是否原生」，不是「图遍历有多快」。厂商公布的百倍性能数字多不可比；能把图、向量、全文写进同一条查询的产品，才是 AI 时代的知识底座。
  4. 规模不要提前买。面向本体工程的知识库（万级到百万级边）用单机开源版可支撑 2 年以上。分布式集群是有触发条件的选项，不是起点。
  5. 时态是本体工程知识库被低估的刚需。「谁在什么时候负责什么」天然是带有效期的边。原生双时态产品，或在 LPG 上自建 valid_from / valid_until，比事后补审计便宜一个数量级。
  6. 70% 的成本不在数据库，在治理。owner 制度、实体消解、Ontology 演进、权限边界决定知识库生死；数据库选型只占其中约 30%。
  7. 给本团队的结论：以开源属性图（Neo4j Community / ArcadeDB 一类）单机起步做 PoC → 引入时态边与 Agent Memory → 向量旁挂 → 由「规模 / 权限 / 信创」任一触发点再决定是否上分布式或企业版。不要一上来采购企业版。

01

问题界定：你到底需不需要图数据库

选型的第一步不是列候选产品，而是确认「图」这个形态在你的查询负载里占多少比重。这一步做错，后面所有工作都是沉没成本。

1.1 四类查询负载，只有一类真正需要图

负载类型典型问题更合适的技术图数据库加分
多跳关系推理「A 和 B 是什么关系」「这个指标口径变更影响了哪些看板」「受过期证书影响的服务有哪些」图遍历（原生邻接）显著
精确事实查询「X 的负责人是谁」「这个项目的牵头团队」关系库主键 / 索引基本没有
语义相似检索「有没有类似的案例 / 历史工单」向量库不适用
全局聚合与社群发现「这几个业务域怎么聚类」「中心度最高的系统是哪个」图计算 OLAP（GDS / 图算法）明显

判断口径：审计你 top 50 高价值问题，统计其中「需要跨 2 跳以上关系才能回答」的比例。低于 20%，先别上图；高于 40%，图数据库就是刚需。

1.2 四种应当先排除的反模式

反模式 A

文档问答为主

问题 90% 是「这份材料里怎么写的」。向量库或 LLM Wiki 就够，上图只会增加抽取成本和维护面。

反模式 B

实时数据入图

价格、库存、订单状态应走 Function Call 直连 OLTP。写进图库既拖慢也污染知识层。

反模式 C

关系浅且规模小

关系深度不超过 2 跳、实体少于百万级时，关系库的 join 与索引更省事、更便宜。

反模式 D

没有 owner 与更新机制

知识库的成败 30% 在技术、70% 在运营。没有责任人和审核流程，换任何数据库都会迅速腐化。

1.3 代价意识：GraphRAG 不是免费的

维度公开数据对选型的含义
索引成本完整 GraphRAG 抽取的 LLM 调用量约为基线 RAG 的 3–5 倍抽取管道要和数据库解耦，可重建、可增量
收益场景微软 GraphRAG 论文：综合型问题准确率 72% → 91%；纯向量在多跳问题上准确率会掉到 30–40%收益集中在多跳与跨文档综合，不是普涨
降本方向LazyGraphRAG（2025-06 起进入 Microsoft Discovery）宣称对比向量 RAG / RAPTOR / LightRAG / 标准 GraphRAG 达 96/96 胜出「惰性索引」正在成为商业产品标配，选型时看厂商跟进度
致命门槛实体消解准确率低于 85% 时，图会「自信地」生成错误关系比数仓坏数据更危险——错误是推出来的，且同样笃定
市场节奏业内测算 2026 年约 85% 企业将采用「向量 + 图」混合；但真正走出试点的知识图谱项目仍少于 15%别拿行业渗透率当自己的可行性证明
注意口径上表中「85% 采用率」为厂商与研究机构测算，非实测量；「3–5 倍成本」「72%→91%」来自公开论文与厂商材料，可作为量级参考，不可作为验收承诺。
02

第一性问题：RDF/OWL 还是属性图（LPG）

这是整份报告最重要的一章。选错模型，后面的产品对比全部作废——因为 RDF 与 LPG 的候选池几乎不重叠。

2.1 两派的本质差别

RDF / OWL 语义库主谓宾三元组 + 本体（TBox/ABox）。模式层是一等公民，原生带推理与约束。查询用 W3C 标准 SPARQL。
VS
LPG 属性图节点 + 有向边 + 属性。关系是一等公民，schema 可选、更贴近业务建模。查询用 Cypher / ISO GQL。

2.2 十维对比

维度RDF / OWL 语义库LPG 属性图
数据模型三元组 / 四元组，URI 全局标识，天然可合并跨源数据节点 + 关系 + 属性，可嵌套、可携带大量业务字段
模式层本体即一等公民，schema 与实例分离（TBox / ABox）schema 可选；约束通常落在应用层或 DB 约束
查询语言SPARQL 1.1 / 1.2（W3C 标准）Cypher · ISO GQL（39075:2024）· Gremlin · GSQL
推理能力OWL 2 DL / RL 原生推理（Stardog / GraphDB / AllegroGraph）无标准推理；靠图算法、规则引擎或应用层补齐
约束验证SHACL 一等公民，事务期可校验应用层校验，或数据库自身的属性/唯一性约束
时态能力部分产品原生双时态（XTDB / TerminusDB / Fluree）普遍需自建 valid_from / valid_until（Graphiti 模式）
生态与人才医药、金融、出版、学术；人才窄、招聘难生态最大，开发者存量最广，上手快
深链性能一般（推理与物化有开销，需调优）强（原生邻接，多跳优势明显）
许可与 TCO主流商业库价格高（Stardog / GraphDB 企业版量级 $50k+/年）开源选项多，可从零成本单机起步
最佳场景合规可证明、跨源数据融合、行业标准本体驱动知识库 + GraphRAG、风控网络、数据血缘、Agent Memory

2.3 决策规则：四个问题定方向

#问题若为「是」
1需要本体层面的形式化推理（从已存事实推出未显式存储的事实）或一致性检查？认真评估 RDF / OWL
2有法规要求可证明的推理链（监管审计、合规判定需展示推导路径）？认真评估 RDF / OWL
3已持有或必须对齐行业标准本体 / 受控词表（FIBO、SNOMED CT、DCAT、PROV-O 等）？认真评估 RDF / OWL
4需要对外发布 SPARQL 端点或链接数据（IRI 可解引用）？认真评估 RDF / OWL
判定四问全否 → 选 LPG。任一为「是」→ 进入 RDF 短名单（Stardog / GraphDB / AllegroGraph / Fluree），并接受更高的许可成本与更窄的人才池。

2.4 三种中间态：不必非黑即白

中间态 A

LPG + 语义层插件

如 Neo4j 的 neosemantics（n10s），换取 RDF 导入导出与 SPARQL 互操作，但拿不到原生推理。适合「要互操作、不要推理」。

中间态 B

RDF + 虚拟图

如 Stardog virtual graphs、R2RML 映射，把关系库当图查而不搬迁数据。适合已有多源异构库、不愿建第二份数据。

中间态 C

分类型混合建模

阿里 OpenBG 做法：类目属性走 RDF/OWL，场景人群走 SKOS，商品品牌关系走属性图。不必用一种模型装全部知识，代价是两套治理。

给本体工程知识库的提醒「本体」不等于「必须用 RDF」。本体工程的核心产出是可校验的业务语义层；用 LPG + 强 schema 约束 + 应用层校验，同样能承载本体工程的治理目标，而且开发与运维成本低得多。RDF 的价值在推理与标准互操作，不在「更本体」。

4.3 时态与版本原生（本体工程最相关的一组）

Bitemporal

XTDB

同时保存事务时间与有效时间，Datalog 图查询，支持按任意历史时点查询，可为隐私合规做数据驱逐。适合「必须回答：你当时知道什么、什么时候知道的」。

Git for data

TerminusDB v12

Apache 2.0（DFRNT 接手维护）。提交 / 差异 / 推送 / 合并 / 时光倒流查询，WOQL Datalog + 闭世界 RDF；v12 加入任意精度小数与 ISO8601 Allen 区间代数。

Verifiable

FlureeDB

事务可签名（JWS / 可验证凭证），提交链内容寻址、防篡改。策略本身是 RDF、随数据版本化并可查询。同一二进制内含 MCP server。

LPG 侧方案

Graphiti 模式

Neo4j 之上给每条边加 valid_from / valid_until / superseded_by，实现「Agent Memory + 时态过滤」。这是最贴近落地、成本最低的时态路线。

注意

时态不是数据库特性而是建模决策

多数 LPG 产品不内置时态语义。若不从一开始就在边上加时间窗，后期补齐要重洗全图。

落地建议：面向公共业务研发中心的路径

本章把通用方法收敛到本团队的实际情况。核心判断：当前阶段不宜重资产自建，应做「轻底座 + 强治理 + 可迁移」。

6.1 现状诊断

维度现状对选型的约束
知识底座LLM Wiki（Markdown + Obsidian），raw 只读真相层 / wiki 编译层 / schema 契约层三层结构已成型图库是第二阶段的事，不是起点；现在引入会打断知识积累节奏
本体资产schema/ontology 已定义 9 类实体、13 类关系，且刻意对齐 Semantic Graph 范式、预留了导图接口已具备「直接导入图库」的模型基础，无需重做建模

资源约束无专职 DBA / 图工程师编制拒绝需要集群调优、分片设计的分布式方案作为起点

6.2 三阶段演进路径

P0 · 0–1 个月｜不引入新数据库把 schema/ontology 从文档升级为机器可读形态（TTL / JSON），脚本导出 Wiki 三元组快照；同时建立 50–200 条 Golden QA 评测集——没有评测集，后面所有验证都无法判断好坏。
P1 · 1–3 个月｜单机 PoCNeo4j Community 单机（GPLv3，零许可成本）或 ArcadeDB（Apache 2.0，无数据量上限）。导入 Wiki 实体关系，跑通多跳查询、Ontology 合规校验、时态查询三个场景。目标：覆盖 Top 50 高频问题。
P2 · 3–9 个月｜时态 + 混合检索按 Graphiti 模式给边加 valid_from / valid_until；向量走 Neo4j 原生 HNSW 或旁挂 Qdrant / Milvus；加 Query Router 实现「图遍历 / 向量 / 结构化」三路路由。这一步产出的是可向业务方演示的能力。
P3 · 9–18 个月｜企业化（触发式）仅当「规模 > 1 亿边 / 需要五层权限与审计 / 出现信创要求」任一触发时，才评估分布式集群或企业版（Neo4j Enterprise、NebulaGraph、TuGraph）。未触发不动。
贯穿全程｜治理 > 技术知识域 owner 制度、实体消解规则、Ontology 变更评审、评测集回归。这四项占据 70% 成本，也决定项目能否活过第二年。

6.3 一句话选型结论与触发条件

主线选择以 Neo4j（LPG + Cypher，GQL 就绪）为主线起步，向量旁挂，时态用 Graphiti 模式实现，规模与权限需求触发后再迁移或升级。理由是：Cypher 技能与 GQL 标准收敛、生态与人才存量最大、GraphRAG 集成最成熟、社区版零成本可验证——而本阶段的瓶颈在语义治理，不在引擎性能。
触发条件切换到为什么现在不切
边规模持续超过 1 亿 / 单机延迟不达标NebulaGraph · HugeGraph（分布式）当前数据量在单机舒适区，分布式带来的是纯运维成本
出现信创 / 国产化硬要求TuGraph · Galaxybase无此要求时，Cypher 生态与人才优势更值钱
需要 OWL 形式化推理 / 合规可证明Stardog · GraphDB当前本体是「约束 + 校验」需求，不是「推理」需求
合规审计要求「可验证、防篡改」Fluree · XTDBMarkdown 层的 as_of + 进度历史已能覆盖当前审计诉求
需要五层权限 + 多租户 + 审计日志Neo4j Enterprise · 或自建权限代理当前使用者范围可控，权限可在应用层先兜住

6.4 向上汇报的口径建议

  • 别谈数据库，谈能力。对决策层的话术不是「我们选 Neo4j 还是 NebulaGraph」，而是「用最小成本把知识库从不可查变成可查、可审、可复用」。
  • 本期只承诺 PoC 里程碑：3 个月内、覆盖 Top 50 高频问题、零许可采购。
  • 价值口径用「建议采纳率 × 采纳后增量收益」，而不是「图数据库性能提升多少」——后者不是本团队的收益语言。
  • 把「不买」讲成决策。明确说明为何当前不采购企业版（成本、试用周期、供应商锁定风险），比含糊其辞更能建立专业信任。

8.2 许可陷阱清单

逐条核对
  • Neo4j 社区版是 GPLv3，不是 Apache 2.0。大量对比表写错。若要嵌入产品并再分发，GPLv3 的传染性必须评估；企业版许可正由美国第九巡回法院审理。
  • 开源 ≠ 生产可用。Neo4j Community 无集群、无在线备份、无 RBAC / LDAP——四项生产必需能力全部缺失。
  • GraphDB Free 11.0 起需申请无费许可，且限制为本地部署、单核、2 并发查询 / 5 仓库，无 LDAP / Kerberos / OAuth / 细粒度权限 / HA 集群；RBAC 与联邦位于付费扩展中。
  • Memgraph（BSL 1.1）与 FalkorDB（SSPL）不是 OSI 认可的开源许可，用于商业分发前需法务确认。
  • Fluree 为 BSL 1.1，按版本首发满 3 年后转 Apache 2.0——是「延后开源」模式，需评估你的使用场景是否落在限制范围内。
  • 供应商退出风险真实存在：Kuzu 于 2025-10 归档（Apple 收购其公司）、RedisGraph 于 2025-01 停服。选任何非头部产品，都要预留退出预案（导出格式、Cypher 核心语法兼容性）。
  • 开源内核与商业版存在代差。NebulaGraph 企业版 v5.2 与 GitHub 内核 release 版本不一致；HugeGraph 亦有社区 / 企业分层。选型必须以开源分支实测为准。

8.3 七个会翻车的技术点

01 致命

实体消解精度不足

准确率低于 85% 时，图会主动推出并笃定地呈现错误关系——比数仓坏数据更危险，因为它看起来同样可信。

02 常见

基准失真

2 跳 vs 5 跳、厂商调优 vs 默认配置、官方审计 vs 自测。三个变量任一不同，结论就不可比。

03 架构

把 RDF 和 LPG 当可互换

两种模型的查询工作流差异巨大，上线后再换意味着重建整个检索层。

04 性能

超级节点

度数十万的节点会让邻域遍历爆炸。需要限定返回集、采样（如 SAMPLE 子句）或切分策略。

05 治理

事后补权限

权限模型必须与 Ontology 同期设计。上线后再补，成本是设计期的数倍，且极易出安全事故。

06 审计

忽视时态

不从一开始在边上加时间窗，历史状态无法回溯，审计需求出现时只能重灌全图。

07 演进

Schema 刚性

强 schema 产品（如 Kùzu 式声明式节点/关系表）在分析场景是优势，在探索式摄取场景是持续摩擦。

08 组织

无 owner 无评测集

知识库 70% 的成败在运营机制。没有明确责任人与回归评测，任何引擎都会在半年内腐化。

8.4 三条采购原则

  1. 先试后买。用 AuraDB Free / 社区版 / 免费版做起，3 个月 PoC 跑完 §7.2 的 12 项再谈合同。
  2. 保持可迁移。把 APOC / GDS / 时态扩展等厂商专有调用藏在薄抽象层后；索引 DDL 放进迁移脚本而不是应用代码。核心 MATCH / CREATE / MERGE / WHERE / RETURN 语法跨 openCypher 引擎可移植，专有部分不可移植。
  3. 只买触发点。规模、权限、合规任一触发才升级。为「未来可能的十亿节点」提前采购，是这类项目最常见的浪费。
09

趋势判断：2026–2028

选型不只看今天的产品清单，还要看未来 18 个月哪些能力会变成基线、哪些产品会掉队。

趋势 01 · 标准

GQL 成为默认查询语言

ISO/IEC 39075:2024 于 2024 年 4 月发布，是第一门继 SQL 之后的 ISO 数据库查询语言；Cor 1:2026 已出，第 2 版委员会草案在编（意见征集已于 2026-01 结束）。Neo4j 的 Cypher 25 已引入 GQL 一致特性，主流厂商陆续跟进；Gremlin 与 GSQL 属独立语言族，无直接迁移路径。选新库先看 GQL 就绪度。

趋势 02 · 能力

「图 + 向量」融合成为基线

Neo4j 原生 HNSW 向量索引、NebulaGraph v5.2 宣称单查询内完成图 + 向量 + 全文混合、HugeGraph-AI 融合向量检索、FalkorDB 与 Fluree 均原生内置。2026 年的判断标准不再是「支持不支持向量」，而是「能否在一条查询里同时用图约束和向量相似度」。

趋势 03 · 竞争

云数仓内置图挤压中低端

BigQuery Graph 2026-04 公测（ISO GQL，属性图即逻辑视图，零数据搬迁）、Spanner Graph、Fabric Graph、Oracle 23ai SQL/PGQ、PostgreSQL + AGE、DuckPGQ——「轻量图谱」越来越不需要专门引入一套数据库。纯图数据库的市场会被推向深链性能与语义治理两个高端。

趋势 04 · 差异化

时态与可验证成为新卖点

XTDB 的双时态、TerminusDB 的 git-for-data、Fluree 的可验证凭证与引擎内策略——在 AI 要为自己的回答负责的时代，「这个结论基于哪个时点的哪些事实、是谁写入的」正在从加分项变成必需品。

趋势 05 · 工具链

本体工具链回暖

OWL / SHACL / 受控词表从学术走进工程；Stardog、Graphwise、AllegroGraph 与行业标准本体（FIBO、SNOMED CT、DCAT、PROV-O）重新被企业采购提及，主要驱动力是合规与可解释性。

趋势 06 · 风险

整合与退出风险上升

Kuzu 归档（Apple 收购）、RedisGraph 停服、Ontotext 与 Semantic Web Company 合并为 Graphwise。市场在向头部集中，中小产品的「由谁维护」要写进尽调清单——这直接决定你三年后是否要重做一遍。

一句话总结趋势未来的图数据库竞争不在「谁遍历得更快」，而在三件事：能不能一条查询完成混合检索、能不能把权限与审计做进引擎、能不能让本体（业务语义）成为可演进的资产。前两件是产品能力，第三件只有你自己能做。

A · 术语速查
LPGLabeled Property Graph，带标签的属性图。节点与边均为一等公民、可携带属性。
RDFResource Description Framework，主谓宾三元组模型，W3C 标准。
OWLWeb Ontology Language，本体语言，支持形式化推理（DL / RL 等子集）。
SHACLShapes Constraint Language，对 RDF 图做形状与基数约束校验的 W3C 标准。
SPARQLRDF 图的 W3C 标准查询语言，1.1 / 1.2 版本。
Cypher / openCypherNeo4j 提出的声明式图查询语言，2015 年开放为 openCypher。
GQLISO/IEC 39075:2024，首个继 SQL 之后的 ISO 数据库查询语言，面向属性图。
TBox / ABox本体中的术语公理集（模式）与断言公理集（实例）。
实体消解Entity Resolution，判定不同来源的多个指称是否指向同一真实实体。
双时态Bitemporal，同时记录「事实生效时间」与「数据库知晓该事实的时间」。
GraphRAG用知识图谱增强检索生成，补齐向量检索在多跳推理上的短板。
LDBCLinked Data Benchmark Council，图数据领域的标准化基准组织（SNB / LSQB / Graphalytics）。
B · 一页速查：这 20 款分别什么时候选
  • 要生态、要人才、要 GraphRAG 集成，规模不大 → Neo4j（注意社区版是 GPLv3 且无集群 / 无 RBAC）
  • 千亿点边、原生分布式、要国产开源 → NebulaGraph / HugeGraph / TuGraph
  • 有信创硬要求 + 金融级一致 → TuGraph / Galaxybase
  • 要 OWL 形式化推理、合规可证明 → Stardog / GraphDB / AllegroGraph
  • 要可验证、防篡改、权限在引擎内 → Fluree
  • 要双时态、回答「你当时知道什么」 → XTDB
  • 要 git-for-data、分支合并、时光倒流 → TerminusDB
  • 数据已在云数仓、不想加系统 → BigQuery Graph / Spanner Graph / Fabric Graph / PostgreSQL + AGE
  • 要宽松许可 + 多模 + 可嵌入 → ArcadeDB
  • 要亚毫秒内存态 + 流式接入 → Memgraph（BSL）/ FalkorDB（SSPL）
  • 要托管、少运维、愿意付费 → Neo4j AuraDB / Amazon Neptune / 华为云 GES / TigerGraph Savanna
  • 要真实业务基准背书 → 查 LDBC 官方审计名单（如 Galaxybase 2022 SNB），而非官网宣传页
